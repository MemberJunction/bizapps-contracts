This table is where the agreement is decided, not where an order is entered. Product, how it is covered, which subscription type it becomes (ContractLine.SubscriptionTypeID — orders' Subscription.SubscriptionTypeID is NOT NULL, so the engine cannot materialize one without it), the coverage window and the negotiated price are all contract provisions chosen here. "Materialized" is the read-only result: the subscription the engine created, flagged contract-billed so orders' own renewal spawner leaves it alone.
Settled: a contract discount OVERRIDES, it does not stack (Amith, 2026-08-04). Orders owns the discount mechanics; the contract states the negotiated intent that outranks whatever would otherwise apply beneath it in the order. So this column IS the whole discount story for a covered line — which is why it is safe to show it here as the operative number. (Stored 0–1: "10%" is 0.10.)

This panel does not exist in MJ yet — it is the one component this app has to build. MJ ships mj-file-browser, mj-files-grid and mj-files-file-upload in @memberjunction/ng-file-storage, but they are category-scoped: nothing in the MJ Angular tree queries __mj.FileEntityRecordLink at runtime (the only references are the generated CRUD forms for the link entity itself). So "files attached to THIS record" needs a small <mj-record-files> component taking EntityName + RecordID. It is a strong MJ-base candidate — every app that acquires paper wants it — so it should be built to donate upward rather than living privately in contracts.

Why the "Attached to" column exists. The contract, each term and each amendment are separate records, and each links its own files through the same EntityID + RecordID pair. This view rolls them up so a person looking for "the paper on this agreement" finds all of it in one place, while the Terms tab still shows only that term's paper.
